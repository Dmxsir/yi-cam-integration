## 1. Final product architecture — locked

The final product is a **Home Assistant App (formerly Add-on) + Home Assistant custom Integration**.

```text
YI Home App = backend / engine / native runtime
YI Home Integration = Home Assistant UI / devices / entities / config flow
Frigate = optional downstream RTSP consumer
```

The development laptop, shell scripts, systemd and manually edited go2rtc YAML are validation infrastructure only. They are not the final UX.

### App responsibilities

- YI account/cloud login backend.
- Automatic camera discovery.
- Capability probing and cache.
- PPPP/TNP sessions.
- Per-camera lifecycle supervisor / restart isolation.
- Native runtime (`libPPPP_API.so`, QEMU, native worker, FFmpeg).
- Managed go2rtc publisher / RTSP publication.
- Persistent state under Home Assistant App `/data` later in Phase 6D.
- Versioned internal API `/api/v1/...`.

### Integration responsibilities

- Config Flow / user-facing setup.
- Discover the App through Home Assistant Supervisor/App discovery.
- User enters YI Home account credentials in the Integration UI.
- Integration sends those credentials to the App through the authenticated internal API.
- One HA Device per camera, identity based on immutable `stable_id`.
- Camera entities, status/sensors, restart/reprobe controls and diagnostics.
- Integration must not load native PPPP libraries, QEMU, FFmpeg or manage camera processes.

### Target onboarding flow

```text
Install YI Home App
  -> App starts and advertises internal connection information
  -> Add YI Home Integration
  -> Integration automatically finds the App
  -> user enters YI account/password/region if needed
  -> Integration sends credentials to App via authenticated internal API
  -> App logs in to YI Cloud and discovers cameras
  -> Integration receives secret-safe inventory
  -> HA Devices / camera entities are created automatically
```

No UID, DID, raw model, TNP version, RTSP URL, YAML, Android phone, ADB or SD-card hack should be required from the user.

## 5. Most recent Phase 6C.5A test and diagnosis

First isolated media-publisher run used:

```text
Backend API: 127.0.0.1:18102
go2rtc API:  127.0.0.1:11984
go2rtc RTSP: 127.0.0.1:18554
```

Production ports `1984/8554` were explicitly untouched.

Observed:

```text
managed_publisher_ready=PASS
managed_publisher_stream_count=7
start_http=PASS
mpegts_ingest_attached=PASS
runtime_pid_initial=9887
RTSP DESCRIBE -> 404
managed go2rtc: streams: unknown error
```

Camera/native logs proved PPPP/TNP and MPEG-TS were good:

```text
PPPP_Connect success
TNP auth PASS
phase3g_media_readers=STARTED
mpegts_mux=STARTED
mpegts_stdout_first_chunk_bytes=32768
media_started=true
```

### Root cause

This was a readiness race, not a camera or PPPP failure.

In go2rtc incoming MPEG-TS:

1. `POST /api/stream.ts?dst=<stream>` starts.
2. go2rtc calls `mpegts.Open(r.Body)`.
3. MPEG-TS probing can run for up to ~5 seconds.
4. Only after probing does go2rtc call `stream.AddProducer(...)`.
5. RTSP DESCRIBE before producer registration sees the configured stream but no producer and may return `streams: unknown error` / 404.

Our first implementation incorrectly considered the publisher attached as soon as HTTP headers were sent / bytes grew.

### Fix already committed

`yi_media_publisher.py` now checks go2rtc `/api/streams?src=<stream>` and reports real producer state.

Publication metadata now includes concepts such as:

```text
producer_registered
mpegts_producer_count
```

The media-publisher smoke test now waits for actual go2rtc MPEG-TS producer registration before running RTSP ffprobe.

Important recent commits:

