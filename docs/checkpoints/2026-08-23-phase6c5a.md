## 1. Final product architecture — locked

The final product is a **Home Assistant App (formerly Add-on) + Home Assistant custom Integration**.

```text
YI Home App = backend / engine / native runtime
YI Home Integration = Home Assistant UI / devices / entities / config flow
Frigate = optional downstream RTSP consumer
```

The development laptop, shell scripts, systemd and manually edited go2rtc YAML are validation infrastructure only. They are not the final UX.

### App responsibilities

- YI account/cloud login backend.
- Automatic camera discovery.
- Capability probing and cache.
- PPPP/TNP sessions.
- Per-camera lifecycle supervisor / restart isolation.
- Native runtime (`libPPPP_API.so`, QEMU, native worker, FFmpeg).
- Managed go2rtc publisher / RTSP publication.
- Persistent state under Home Assistant App `/data` later in Phase 6D.
- Versioned internal API `/api/v1/...`.

### Integration responsibilities

- Config Flow / user-facing setup.
- Discover the App through Home Assistant Supervisor/App discovery.
- User enters YI Home account credentials in the Integration UI.
- Integration sends those credentials to the App through the authenticated internal API.
- One HA Device per camera, identity based on immutable `stable_id`.
- Camera entities, status/sensors, restart/reprobe controls and diagnostics.
- Integration must not load native PPPP libraries, QEMU, FFmpeg or manage camera processes.

### Target onboarding flow

```text
Install YI Home App
  -> App starts and advertises internal connection information
  -> Add YI Home Integration
  -> Integration automatically finds the App
  -> user enters YI account/password/region if needed
  -> Integration sends credentials to App via authenticated internal API
  -> App logs in to YI Cloud and discovers cameras
  -> Integration receives secret-safe inventory
  -> HA Devices / camera entities are created automatically
```

No UID, DID, raw model, TNP version, RTSP URL, YAML, Android phone, ADB or SD-card hack should be required from the user.

### Corrected root cause

The earlier checkpoint diagnosis said RTSP was racing producer registration. The latest run disproved that: a producer was already registered when RTSP returned 404.

Exact go2rtc `1.9.14` revision `b5948cf` behavior was inspected:

1. Incoming `POST /api/stream.ts?dst=<stream>` calls `mpegts.Open(r.Body)`.
2. `mpegts.Open()` starts MPEG-TS probing before `stream.AddProducer(...)`.
3. `core.ProbeTimeout` is exactly **5 seconds**.
4. The MPEG-TS probe loop returns `nil` when the five-second deadline expires, even if no H264/AAC media was discovered.
5. go2rtc can therefore register an MPEG-TS producer whose `GetMedias()` / JSON `medias` is empty.
6. RTSP `AddConsumer()` cannot match any producer media and returns `streams: unknown error`, surfaced as DESCRIBE 404.

Why this happened in our HTTP publisher:

- `_publish_mpegts()` opened and sent HTTP POST headers immediately when the runtime process started.
- That started go2rtc's five-second MPEG-TS probe clock before the camera had completed PPPP connect, TNP authentication, media-reader startup and FFmpeg mux startup.
- In the failing run the first useful MPEG-TS chunk arrived only around the five-second boundary.
- go2rtc could see enough metadata to finish `Open()` and register the producer, but the probe deadline could expire before a usable H264/AAC PES was turned into `medias`.

This explains the otherwise contradictory state:

```text
producer_registered=true
mpegts_producer_count=1
RTSP DESCRIBE=404
streams: unknown error
```

This is an **HTTP ingest probe-clock startup bug**, not a PPPP/TNP failure and not evidence that the MPEG-TS muxer needs to change.

### Fix committed on 2026-08-23

`yi_runtime_lifecycle.py` now prebuffers the first **64 KiB** from supervised MPEG-TS stdout **before opening the HTTP POST** to go2rtc. The first chunk is sent immediately after request headers. This prevents PPPP/TNP camera startup time from consuming go2rtc's five-second MPEG-TS probe window.

`media_publisher_attached` now becomes true only after the first actual MPEG-TS chunk has been sent, rather than after headers alone.

`yi_media_publisher.py` now reports both registration and media readiness:

```text
producer_registered
mpegts_producer_count
producer_media_ready
mpegts_ready_producer_count
```

`producer_media_ready=true` requires an MPEG-TS producer whose go2rtc JSON includes at least one `media` entry.

The Phase 6C.5A smoke now waits for **media-ready** producer state before RTSP ffprobe, so a producer with `medias=[]` can no longer produce a false PASS marker.

Regression tests added:

- `tests/test_yi_runtime_lifecycle.py` — verifies the first pipe read occurs before HTTPConnection creation and 64 KiB are published.
- `tests/test_yi_media_publisher.py` — verifies an MPEG-TS producer with empty `medias` is registered but not media-ready.

