## 4. Important 6C.5A bug/fix retained

go2rtc 1.9.14 revision `b5948cf` uses a five-second MPEG-TS `ProbeTimeout`.

Opening incoming HTTP ingest before PPPP/TNP startup completed could consume that probe window before useful TS PES arrived. go2rtc could then register a producer with `medias=[]`, causing RTSP `DESCRIBE` 404 / `streams: unknown error` even though `producer_registered=true`.

Fixes now present:

- `yi_runtime_lifecycle.py` prebuffers the first 64 KiB MPEG-TS chunk before opening the go2rtc HTTP POST.
- `yi_media_publisher.py` exposes:
  - `producer_registered`
  - `mpegts_producer_count`
  - `producer_media_ready`
  - `mpegts_ready_producer_count`
- smoke tests require `producer_media_ready=true`, not registration alone.

Do not regress this behavior.

## 6. Fault injection design

The test does **not** use global `pgrep qemu` or signal arbitrary QEMU processes.

It:

1. Records the selected fault camera lifecycle PID.
2. Walks `/proc` descendants of that PID only.
3. Requires exactly one `qemu-aarch64` descendant.
4. Sends `SIGSTOP` only to that descendant.

Why this should exercise the real recovery path:

- `yi_native_session_supervisor.py` starts the relay in its own session/process group.
- The relay starts QEMU as a descendant in that relay process group.
- Freezing QEMU stops fresh native media.
- The existing supervisor should detect media silence after its stall timeout.
- Supervisor terminates the relay process group and exits `75`.
- `YiRuntimeLifecycleManager` sees the supervised runtime exit while `desired_running=true`, increments restart state and creates a fresh session.

The test also verifies the original frozen QEMU descendant is gone after recovery.
